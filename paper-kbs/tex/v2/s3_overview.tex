\section{Platform architecture}
\label{sec:system}

\subsection{Design principles}
QDCVR (v2.3) is a self-hosted platform that turns a folder of PDFs, Office
documents, and scans into knowledge bases that agents can be trusted to
answer from. Five principles shape the architecture (Fig.~\ref{fig:arch};
Table~\ref{tab:modules} maps every module to its responsibility and the
design decision that shapes it):

\begin{description}
\item[P1 -- Content-routed organization.] Documents are organized by what
they \emph{say}, not by which folder they sat in: ingestion derives tags and
a five-field description from the extracted content, and retrieval starts
from a library catalog rather than a directory path.
\item[P2 -- MCP-first machine interface.] Every capability is exposed as a
tool of a Model Context Protocol server \cite{mcp}: 97 tools in eight groups
(search, graph, judging, experience, persona management (SOUL),
ingestion/\allowbreak parsing, library lifecycle, filesystem/\allowbreak tags). Web, HTTP, CLI, and MCP clients sit on
the same layer, so a capability added once is available to every harness.
\item[P3 -- Verification before promotion.] No similarity score, however
high, promotes a document into an answer; a judging model must read the
candidate's fetched content and vote. Verdicts fail closed: missing text,
engine errors, or timeouts reject the candidate rather than pass it.
\item[P4 -- Honest abstention.] When verification eliminates every
candidate, the system returns an explicit not-found report listing what was
searched and what was not covered. Refusing to answer is a terminal success
state, not an error path.
\item[P5 -- Engine-agnostic agency.] Answer agents are pluggable harnesses
(14 adapters, e.g.\ \texttt{omp}, Claude, ACP-compatible CLIs); the platform
constrains them through tool whitelists and prompts, never by coupling to a
particular vendor.
\end{description}

\subsection{Ingestion pipeline}
Ingestion is a nine-step, quality-gated flow executed by an archival
sub-agent through MCP tools: (1)~pre-flight tool probing; (2)~duplicate
detection (exact SHA-256 plus near-duplicate vector search at $\geq 0.90$
cosine); (3)~a library census; (4)~parsing with MinerU \cite{mineru} (local
OCR engine for scanned PDFs, direct reading for Markdown/text); (5)~a
semantic split gate for documents beyond 30\,000 characters (the agent
proposes split boundaries; a validator enforces a 0.85 target utilization
and forbids oversized atomic units); (6)~content-derived tagging and
description; (7)~multi-channel indexing (vector + graph + BM25); (8)~a
post-condition check that the new document is actually retrievable; and
(9)~an audited report. Two design choices matter in practice. First,
descriptions are generated by reading the content, and the retrieval layer
treats them as \emph{claims to be verified} rather than truth --- in an
audit of 26 document descriptions on a predecessor corpus, 24 were found to
mismatch their documents' actual content (released audit logs). Second,
indexing success is judged by observable effects (\texttt{total\_chunks}
$> 0$), because we observed GPU out-of-memory failures that returned
success envelopes with empty index payloads.

\subsection{Storage and service layers}
Four stores back the platform. A tree filesystem holds Markdown documents
with a metadata registry (library states, document paths, tags); per-library
ChromaDB collections index BGE-M3 embeddings \cite{bge-m3,chroma} (1024-d,
cosine space, 500-char chunks with 50-char overlap); Neo4j \cite{neo4j}
maintains the Document/KnowledgeBase/Tag graph with weighted
\textsc{RelatedTo} edges derived from shared tags, vector similarity, and
agent judgments; and a jieba-tokenized BM25 inverted index \cite{bm25}
supports lexical matching. Domain services wrap these stores: the vector
service serializes writes per collection (we traced one production incident
to concurrent HNSW segment handles), the two-stage service fuses BM25 and
graph expansion for candidate generation before a dense refine stage, the
experience service versions operational lessons as first-class documents
with their own retrieval threshold, and the verification gate is served by
a resident judge worker whose engineering details appear in
Section~\ref{sec:impl}.

remainder of this section walks through the layers, and

operational engineering built on top of them.

\subsection{How a query flows through QDCVR: one trace}
\label{sec:trace}
Figure~\ref{fig:arch} shows the components; this subsection makes them
concrete by following one real question end to end. The question is Q2 of
Section~\ref{sec:setup} --- \emph{``EL inspection shows edge delamination:
root cause and corrective actions''} --- asked through the public chat API
with the failure-analysis library pinned and the Hybrid lane selected.

\begin{enumerate}
\item \textbf{Request and policy.} The chat endpoint inspects the request and
attaches the Hybrid lane's tool whitelist and instructions. Because the
whitelist is enforced server-side, the agent physically cannot call a tool
outside it --- the lane is a property of the enforcement layer, not of prompt
discipline.
\item \textbf{One orchestrated call.} The agent issues a single
\texttt{kb\_hybrid\_search}. Both candidate channels then run server-side: a
dense vector channel (top-30, cosine threshold 0.35) and a catalog keyword
channel over the pinned library's descriptions.
\item \textbf{Merge and cap.} Candidates are merged on (library, document),
documents agreed by both channels are ordered first, and the pool is capped at
twelve. On Q2 the pool is twelve documents: the gold root-cause report plus
eleven same-domain siblings.
\item \textbf{The verification gate.} The server fetches each candidate's full
text itself --- the agent never supplies text, so it cannot argue for a
document it has not read --- segments it, and scores ``does this text contain
direct evidence that answers the query'' in batches of at most six. On Q2 the
gold report scores 0.846 while five extruder-telemetry reports score
0.887--0.926.
\item \textbf{Cut and read.} A document-level relative cut (keep
$\geq \mathit{best}-0.15$, top-5 floor, cross-domain anchor guard) selects the
kept set, and the top five documents are returned in full ($\leq$2\,000
characters each). This is the only full-content channel the agent sees.
\item \textbf{Answer with provenance.} The same response carries the complete
audit trail (per-channel candidates, merge counts, judge statistics, cut
decisions). The agent composes an answer whose citations name the document
path, the lane, and the engine score, graded P0 (direct evidence) through P2
(weak).
\item \textbf{Failure and abstention paths.} If the cut leaves no survivor,
Lane~A escalates once to Lane~B; if Lane~B also exhausts its twelve-call
budget, the system returns an explicit not-found report rather than a
speculation (\S\ref{sec:abstention}).
\end{enumerate}

The trace also shows \emph{where} the design fails. Under the shipped
re-ranking role, Q2's gold (0.846) is pushed to rank eight by the five
higher-scoring telemetry reports --- outside the five-document read window, so
the agent reads confusers (Fig.~\ref{fig:anatomy}). Under the filter role the
same pool, the same scores, and the same verdicts leave the gold first. Same
gate, same evidence; only the role of the induced ordering changes. This one
trace foreshadows the paper's central result
(Section~\ref{sec:inflation}) and is why it is placed before, not after, the
experiments.
