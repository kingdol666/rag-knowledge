① 系统架构设计图

KBS 系统类论文最常见的「Figure 2/3」：先给一张组件-连接-边界的架构蓝图，再给一张实例化原型图。这是与我们 HMRS 论文最直接对标的图型。

② RAG / 知识检索流水线

把「文档 → 分块 → 向量 → 检索 → 上下文 → LLM → 答案」画成一条带泳道的闭环，是 KBS 检索类论文的标准做法。

③ 执行流程图 / 时序图 / 算法流程图

论文里「系统怎么跑一遍」通常用编号步骤、UML 时序图或判定菱形流程图表达，而不是再画一张架构图。

④ 框架总览、综述结构与风格边界样本

卡片式总览、箭头标题带、以及「不规范」的手绘样本，共同构成 KBS 真实绘图风格的全貌。

⑤ KBS 绘图风格：8 条可验证规律

以下每条都能在本画廊的具体图里找到对应证据，不是泛泛而谈。

#规律证据与说明
1架构图用「标准建模语言」而非自由涂鸦Journalistic KP 的 Fig.3 明确标注 represented with ArchiMate 3.1 notation；HELIOT Fig.4 用 C4/UML 组件图写出 [Component: Streamlit]、[Container: TileDB]、[Software System] GPT-4 API。组件右上角带小图标区分类型，右下角放线型图例。
2「大虚线框 = 系统边界 / 泳道」GTR Fig.1 用两个虚线圆角框分出 USER INPUT 与 MODEL FRAMEWORK；HELIOT 用虚线框圈住整个 Heliot CDSS，把外部 LLM 放在框外；CIR3 用底色带表示 Transactive Memory State。
3中心化布局：知识库居中，其余组件环绕Journalistic KP Fig.2/3 把 Knowledge Base 放正中，Ingestor、Feeder、Retriever、Learner、Curator 分列四周；HMRS 的五层数据模型完全可以用同样的中心辐射式。
4箭头必须带「语义标签」和「线型区分」Journalistic KP 图例区分实线 Trigger direction 与虚线 Information flow；HELIOT 箭头写 Makes API calls [JSON/HTTP]、Reads from [Array API]；Supervisor 图用实线=任务下发、虚线=报告回传。
5配色极度克制，多为单色系 + 少量强调色ArchiMate 图全篇只有青色（#9fe6e3 系）+ 白 + 黑；HELIOT 只有蓝 + 深蓝 + 灰；FinBloom 甚至全灰阶。彩色只用于编码语义（GTR 用红/蓝/黄/绿点区分 query / stored / retrieved vectors；QueryExpansion 用菱形紫色、处理框蓝色、输出框黄色）。
6流程用编号①–⑦、判定菱形与显式反馈回路CIR3 Fig.1 把 7 个步骤直接编号在箭头上，并写出 <K、<L 迭代次数与收敛判定；QueryExpansion Fig.8 用 5 个菱形判定 + TP/FP/TN/FN 出口；DualMemory Fig.1 用黄色菱形 b < b*。
7跨栏大图承载主架构，单栏小图承载辅助流程实测坐标：ArchiMate 主图占整页宽；Journalistic KP Fig.2 高层视图 bbox 仅 (369,560)-(495,695)，是右栏单栏小图。双栏排版下主图一般跨两栏放在页面上部。
8图注写「这张图在做什么」，不止写题名CIR3 图注长达 5 行，逐步解释 (1)–(7)；HELIOT 写 Overview of the Pharmaceutical Data Pipeline Process；GTR 写明 showing our embedding-based retrieval system using document chunking。图注本身就是小摘要。
诚实边界：本画廊里有 3 类样本不是 KBS 正式排版，解读风格时已经区分： A_COMPANION_* 是 CEUR-WS workshop 前驱稿；A_KG_Orchestra_* 是 bioRxiv 预印本； A_GOFAI_* 虽发表于 KBS，但用的是手写体涂鸦风格，属于低规范样本（故意保留作反例）。 另外 KG-Orchestra 的 62 页 PDF 正文完全没有嵌入图形对象，图形集中在 p52–p62 附录，因此不作为风格样本。

⑥ 对 HMRS 论文画图的具体建议

优先级动作依据 / 落地方式
P0主架构图改用 ArchiMate 或 C4 组件图参照 Journalistic KP Fig.3 与 HELIOT Fig.4：五层数据模型 L1–L5 各自画成组件框，框内列子组件，框上标 [Component] / [Container] 类型，用虚线大框圈出「系统边界」，把外部 embedding / LLM 服务放到框外。这比自由画方框更经得起系统类期刊评审。
P0补一张「带编号」的 QDCVR 执行流程图参照 CIR3 Fig.1 与 Supervisor 时序图：把「路由 → 召回 → 内容 Rubric 裁决 → c≤4 丢弃 / c=5 fallback / c≥6 采用 → not-found report」画成 ①–⑦ 带判定菱形的流程，并显式画出 librarian escalation 与 feedback 回路。当前稿件缺的正是这类「系统怎么跑一遍」的图。
P0给每张图配线型图例实线=控制/触发，虚线=数据流/信息流（ArchiMate 图例），并在箭头上写语义标签。HMRS 有 HTTP 写路径与直连文件读路径两条完全不同的通道，必须靠线型+标签区分，否则读者会误以为是同一条数据总线。
P1主图跨双栏、辅助图单栏按实测坐标，跨栏图放在页面上部占满 textwidth；高层概览图可缩成单栏小图。避免把复杂架构硬塞进单栏导致字号小于 8pt。
P1配色统一到单色系 + 1 个强调色建议青/蓝单色系（与 ArchiMate、HELIOT 一致），仅用一种强调色标出「内容裁决」这一创新点（对应 GTR 里用彩色点编码向量类型的做法）。不要每种模块一种颜色。
P1图注写成小摘要像 CIR3 那样在图注里逐条解释编号步骤与判定条件，而不是只写 "Overview of our system"。
P1加一张「原型实例化」图Journalistic KP Fig.4 用真实组件 logo（DBpedia / Wikidata / docker）证明架构可落地。HMRS 可对应放 ChromaDB、Neo4j、BGE-M3、MCP 等真实组件标识，强化 Applied Research / KBS 系统论文最看重的「真的实现了」。
P2避免手写体、曲线箭头、无图例的自由涂鸦GOFAI Fig.3 是已发表但明显低规范的样本；也避免 LGMT 式彩色卡片堆叠用于系统架构（它适合评测框架总览，不适合表达组件连接）。
P2避免把实验结果图当架构图本包中 A_Practical_PrivacyPreserving_Framework 有 22 张图全是通信耗时/请求大小的柱状对比，无一张架构图——这类论文不适合作为绘图风格参照。
