\section{System overview and management model}
\label{sec:system}

HMRS uses the same collection hierarchy to file documents and to guide
retrieval. The parsing service recovers document content, the web application
maintains collections and their files, and the MCP server exposes the managed
state to agents \cite{mcp}. Placement determines where a document is listed;
its description helps the agent decide whether to open it; its index entries
make passages available to lexical and dense search. HMRS distinguishes
several operational states: a document is \textbf{stored} when its file exists,
\textbf{registered} when the tree and collection metadata point to it,
\textbf{indexed} when a corresponding index entry exists, \textbf{query-visible}
when a scoped query returns an identifier for it, and \textbf{traceable} when
returned text resolves to document and span coordinates. An observation at one
state does not establish the next. The document files, tree registry and
collection metadata constitute the managed state; lexical and dense indices,
and the optional graph, are derived projections. File and metadata writes and
index or graph updates are separate, sometimes asynchronous operations, so the
system is operationally eventually consistent across these projections.
Reconciliation checks compare document files, the tree registry and
per-library metadata after selected operations.

\subsection{Management levels and the tiered access path}
\label{sec:levels}

Collections define ownership and scope; documents contain text and
descriptive metadata. An oversized document can be stored in several parts. The index divides
whole documents or their stored parts into segments called chunks. At query time, a passage is any
text span returned or scored. The catalogue lists collections, a shelf lists documents within one
collection, the document view exposes the body, and the segment view exposes
passages with source references. Each level has its own operations and
state checks.

In the implementation, a collection is called a library or knowledge base;
this paper uses \emph{collection} for the managed object and retains
\emph{library} only in implementation terms such as ``sub-library'' and
``library registry.'' The evidence gate is the Laya passage scorer; an
unqualified \emph{judge} in the evaluation refers to the blind answer
evaluator, not the gate.

The ingest agent uses catalogue descriptions to place parsed material and
derives document descriptions and tags from its content. Sub-libraries are
tree nodes with their own descriptions and indices. At the document level,
duplicate review identifies candidates and a lifecycle operation can move,
rename or delete a document. At the segment level, search returns indexed
chunks, while the optional evidence gate fetches candidate text and scores
query-conditioned passages with provenance.

and metadata from retrieval components that consume derived projections. The
ingest agent chooses a collection, the save service validates the destination
identifier, and an audit checks the result that was stored.

\subsection{Data model and object lifecycle}
\label{sec:datamodel}
\label{sec:lifecycle}

Documents are stored as Markdown with associated assets. A managed
collection's state spans the document files, \texttt{.tree-fs.json} and the
library's \texttt{.knowledge-base.yml}. The ingest workflow distinguishes
parsed and stored content from indexed content and, in the reference workflow,
treats material as retrieval-ready only after the relevant indexing operation
and a successful content-based probe. The MCP save path can start background
indexing; the web parsed-file save path exposes indexing as a separate
operation. Graph construction is separate. After a move, rename or reindex,
the file path and metadata show the stored state and a retrieval probe checks
which path the index returns. Sections~\ref{sec:acquisition}--\ref{sec:implementation}
describe these layers in turn: acquisition, organisation and lifecycle, tiered
access and the evidence gate, and the implementation.
